# CritPt migration into DDSR

The migration starts from DDSR `2f5b952` and imports CritPt work through
`93425280f1829bfced2a51ff52f0d0deba540863`. The common ancestor is `aec06de`.
Consensus remains under this benchmark's `evaluation/consensus` package; the
shared benchmark registry, result adapters, reward and training schema retain
DDSR behavior. No historical answer is regenerated by migration.

## Generation and request compatibility

The shared transport now supports independent per-call token limits and seeds,
stream journals and vLLM input-token budgeting. CritPt's static adapter refills
available slots, persists each stage and resumes saved work. The first-stage
content, even when empty, remains the assistant message before the official
formatting prompt. Reasoning text is never recovered as a final answer.

`AliyunClient` defaults to DDSR's original native payload. Migrated DeepSeek
jobs select `request_profile: openai` to preserve the actual old request:
`max_completion_tokens`, explicit `reasoning_effort`, and a per-trial seed;
`temperature` and `top_p` are omitted. API URL and key environment-variable
names do not change. Unsupported options are not silently downgraded.

A normal `--resume` permits only concurrency changes. A job imported from
CritPt can explicitly declare storage mappings:

```yaml
resume_migration:
  path_prefixes:
    /old/critpt-eval/outputs: /shared/critpt/runs/outputs
    /old/tasks: /shared/critpt/tasks
```

These mappings apply only to job output and dataset paths. The compatibility
check recognizes the former CritPt agent namespace and the equivalent
OpenAI-to-Aliyun openai profile. It still rejects changes to model, endpoint,
prompts/strategy, seed, sampling, stage budgets or other generation settings.
Stage reuse additionally checks the saved public problem, request messages and
sampling. A mapped config is saved as a new resume audit, never over the
original `job-config.yaml`.

For a higher formatting budget, create a separate retry directory and reuse
only the first-stage checkpoint with `run_trial(..., resume=True)`. A complete
second-stage checkpoint requires its original formatting budget. Keep the
original trial and replacement audit before selecting any retried result.

## Assets and operational configuration

Local datasets, all 700 original trials, the selected 41 retries, pre-replacement
backups, grading reports and launch snapshots belong in shared assets. This
installation uses `/mnt/workspace/zhizhou/assets/critpt`; DLC mounts the same
storage under `/mnt/nas/zhizhou/assets/critpt`.

- `references/consensus-61-v2.json`: evaluator-only reference asset; its default
  absolute path and SHA-256 are recorded in `evaluation/consensus/bundle.py`.
- `runs/outputs/static/`: original and retry native job directories.
- `runs/outputs/launches/`: immutable launch configs, manifests, logs and source snapshots.
- `runs/grading-original/`: immutable CritPt grading and reference replay reports.
- `runs/grading-ddsr-20260917/`: DDSR validation replay and per-model batch results.
- `migration-20260917/`: source Git bundle, original worktree archive, file hash
  inventory, path map and validation records. The private archive includes local
  configuration and must not be published.

The 41 selected retry results were already copied into the original job
directories before migration. Migration does not repeat that operation. Root
job configs continue to describe the original generation; replacement manifests
explain the selected trials' higher formatting budget.

`configs/local/` holds ignored DSW/DLC job profiles, resume configurations,
retry mappings, serving metadata and an inventory of asset paths. The original
configurations are archived unchanged. New-run profiles use a 131072 formatting
cap and a new job name; resume profiles preserve historical budgets. `.env` is
private and ignored. Portable examples remain versioned under
`configs/jobs/critpt/`, and `scripts/critpt/run_job.py` optionally reads a dotenv
file. `scripts/critpt/run_dlc.sh` accepts mounted source/config/wheel paths and
uses an isolated temporary Python environment. It does not submit cloud jobs.

The model serving repository and model weights remain at their existing shared
locations. Migration does not restart or stop any model service. Historical
logs may contain old paths; active launchers and configs use the DDSR checkout
and shared assets instead.

## Scoring and isolation

`ddsr-critpt-consensus batch` reads one native job, keeps every attempt result,
and averages over all active policy problems and available attempts. For five
attempts the current `consensus-61-v2` denominator is 305. Generation errors,
missing candidates and unknown comparisons count as zero in that mean, while their distinct statuses
and diagnostics remain available. Nine excluded problems are reported as
skipped, including challenges 47 and 51 after the reference audit documented in
[EXCLUSIONS.md](evaluation/consensus/EXCLUSIONS.md). These are internal consensus
match rates, not official accuracy.

The original generation validator is reused byte-for-byte. Helper functions,
`lambda`, and `try` remain prohibited. Missing/invalid answer artifacts retain
the upstream format failure; the scorer does not salvage reasoning text.
Symbolic representation limitations and unknown comparisons retain the same
policy as the source repository.

Docker is the default worker backend. Linux optionally uses bubblewrap,
libseccomp, namespaces, a mount allowlist, dropped privileges, resource limits
and wall-clock termination. It never falls back to execution on the host.
Reference data is stored outside the repository and wheel. The evaluator reads
its configured absolute path (or an explicit `--bundle`); it is not included in
solver build contexts. Linux workers mount only the interpreter, scientific libraries,
package initializers and selected execution modules; they cannot read the
reference bundle, credentials or repository tree.

## Validation and cleanup gates

The original migration validation required unchanged reference/validator hashes,
a full 212-reference replay with 7 skipped slots, and all 700 historical trial
results compared by identity, status, match decision and error category. Its
aggregates were Qwen 60/315 and DeepSeek 92/315 under `consensus-63-v1`.
The current `consensus-61-v2` reference replay has 204 matches and 9 skipped
slots; the same historical trials score Qwen 58/305 and DeepSeek 92/305 after
excluding challenges 47 and 51. See [VALIDATION.md](evaluation/consensus/VALIDATION.md)
for both policy versions and their reference hashes. Unit tests cover request
profiles, seeds, resume rejection, stage checkpoints, batching and OS isolation. The complete
DDSR suite also checks the other three benchmark contracts and export paths.

Before removing the old checkout, preserve its complete Git history and every
non-cache local artifact, verify the shared file inventory, and check active
processes, scripts and symlinks for dependencies on the old path. DDSR's Python
environment must not import code or packages from that checkout. Keep the
recoverable archive and all shared results after removal.

### Recorded migration validation (2026-09-17, before reference externalization)

- 316 tests passed, including all four benchmark contracts and real Linux
  namespace, filesystem, syscall, memory/file limit and worker cleanup tests.
  Black, Ruff and `git diff --check` passed.
- Real Linux reference replay: 212 matched, 7 skipped. All 700 historical trial
  identities, statuses, matches, error details, metadata and candidate hashes
  agree with the original reports. Qwen remains 60/315 (19.047619%); DeepSeek
  remains 92/315 (29.206349%). Their 8 and 5 generation-format failures persist,
  as do DeepSeek's 3 unknown comparisons.
- DDSR collection/trajectory adapters read all 700 native trials; both mapped
  jobs resume without another model call. All recorded stage seeds were checked
  against the original base-42 derivation.
- A real request to the existing Qwen vLLM service passed with xhigh reasoning,
  seed 42 and dynamic token accounting against the native 262144 context.
- Real PAI calls accepted both Aliyun payload profiles with max reasoning and
  seed 42. One pinned CritPt problem exercised the static two-stage path using
  deliberately small 2048-token caps: both stages ended at the cap, leaving a
  recorded format failure. A simple two-stage Harbor-adapter call used the real
  API and simulated environment upload; it produced validated code. No complete
  Harbor container trial or Docker end-to-end replay was run because this DSW
  has no Docker daemon. All four solver build contexts were checked with the
  Docker SDK's exclusion parser.
- The wheel includes reference data, prompt/config assets and existing vendored
  license notices, and excludes secrets, local config and outputs. An isolated
  offline generation environment loads the installed wheel using the shared
  runtime wheels; it does not depend on the former checkout. No GPU deployment
  was created or stopped during migration.
